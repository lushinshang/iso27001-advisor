系統概覽：哪些東西是「ISO 27001 專屬」的？

這套系統的五層架構（快取 → 搜尋 → 推理 → 推薦 → 輸出）完全可以移植。 需要替換的只有「裡面裝的資料」和「顧問的自我介紹」，程式碼的 90% 不需要動。

移植前清單

  • 已安裝 Python 3.10+，可在終端機執行 python3 --version
  • 已安裝 Ollama 並確認 gemma4:e2b-mlx 可正常運作（ollama run gemma4:e2b-mlx）
  • 手邊有新標準的 PDF 原文（例如 GDPR 全文、NIST CSF、內稽規範）
  • 已安裝 docling：pip install docling
  • 已安裝 sentence-transformers：pip install sentence-transformers
  • 大約準備 2-4 小時，大部分時間在等待 AI 處理 PDF
1

複製專案到新資料夾

整包複製，不要在原本的 ISO 27001 版本上直接改。

# 在終端機執行（把 gdpr-advisor 換成你想要的名稱）
cp -r iso27001-advisor gdpr-advisor
cd gdpr-advisor
✅ 建議：用新標準的縮寫命名資料夾，例如 gdpr-advisor、nist-advisor、sox-advisor。 之後兩套系統可以並存，互不影響。
2

清空舊資料

刪除所有 ISO 27001 相關的資料檔，保留程式碼與設定。

要刪除的檔案

data/
├── iso27001_structure.json ← 刪除（ISO 27001 條文）
├── pdca_graph.json ← 刪除（ISO 27001 PDCA 圖譜）
├── knowledge_graph.json ← 刪除（若存在）
├── embeddings.npy ← 刪除（若存在）

3

匯入新知識庫（最重要的步驟）

這步驟把你的 PDF 轉成系統能讀懂的結構化資料。

⚠️ 重要限制：scripts/build_new_advisor.py 目前有兩個已知問題需要先修正，直接跑會產生格式錯誤的資料，系統啟動就會崩潰。 請依照下方指示先修正再執行。

問題 1：輸出路徑錯誤

原腳本輸出到 ../custom_data/，但系統只讀取 data/。

用文字編輯器（記事本、VSCode 皆可）打開 scripts/build_new_advisor.py，找到第 19-20 行：

# 找到這兩行
PDF_DIR = "../new_pdfs"
OUTPUT_DIR = "../custom_data"

# 改成（PDF 放在專案根目錄的 new_pdfs/ 資料夾）
PDF_DIR = "new_pdfs"
OUTPUT_DIR = "data"

問題 2：輸出 JSON 格式不相容

原腳本輸出的檔名是 knowledge_base.json，但系統只認識 iso27001_structure.json。 同時，欄位格式也不一樣。

繼續在同一個檔案裡，找到第 70-73 行，修改檔名並補上系統需要的欄位：

# 找到這段（step1_convert_pdfs 函式末尾）
all_chunks.append({"id": f"doc_{chunk_id}", "source": filename, "content": current_chunk.strip()})

# 改成（加上 type / section / subsection / title 欄位）
all_chunks.append({
    "id": f"doc_{chunk_id}",
    "type": "clause",
    "section": filename.replace(".pdf", ""),
    "subsection": f"段落 {chunk_id}",
    "title": f"段落 {chunk_id}",
    "content": current_chunk.strip()
})

# 同時把輸出檔名改為系統認識的名稱（同函式最後幾行）
kb_path = os.path.join(OUTPUT_DIR, "iso27001_structure.json")  # 改這裡

修改完成後，執行轉換

# 1. 建立放置 PDF 的資料夾
mkdir new_pdfs

# 2. 把你的 PDF 複製進去（手動操作）
#    例如：gdpr_full_text.pdf、nist_csf_2.0.pdf

# 3. 執行自動轉換（會依序完成 PDF → 文字 → 向量）
python3 scripts/build_new_advisor.py
⏳ 時間預估：每份 PDF 約需 3-10 分鐘（依文件長度和電腦速度）。 畫面上會顯示「✅ 轉換完成！共切出 XXX 個段落」代表成功。

（可選）手動建立新領域的 PDCA 圖譜

系統的「合規推薦」功能依賴 data/pdca_graph.json。如果你的新標準有類似的 Plan-Do-Check-Act 循環結構，可以手動仿照原本的格式建立。如果暫時不需要這個功能， 建立一個空檔案即可讓系統不崩潰：

echo '{"nodes":[],"edges":[]}' > data/pdca_graph.json
4

換上新顧問人設

讓 AI 知道自己現在是哪個領域的顧問。需要改三個地方。

① agent.py — LV2 和 LV3 Agent 人設（第 75、87 行）

打開 agent.py，找到以下兩個變數，把「ISO 27001 資訊安全管理系統」改成你的新領域：

# 第 75 行 — LV2 一般顧問對話
LEVEL2_SYSTEM_PROMPT = """你是一位 ISO 27001 資訊安全管理系統顧問..."""
# 改成例如：
LEVEL2_SYSTEM_PROMPT = """你是一位 GDPR 個人資料保護法規顧問..."""

# 第 87 行 — LV3 稽核準備模式
LEVEL3_SYSTEM_PROMPT = """你是一位 ISO 27001 資訊安全管理系統顧問..."""
# 改成例如：
LEVEL3_SYSTEM_PROMPT = """你是一位 GDPR 個人資料保護法規顧問..."""

② llm.py — 主要對話 Prompt（含引用規則）

打開 src/iso27001_advisor/llm/llm.py，找到 get_system_prompt() 函式（約第 187 行）。 這裡有最詳細的顧問行為規範，需要把 ISO 27001 專屬內容換成新領域的術語。

最少需要修改：

  • 第一行「你是一位專業的 ISO 27001 資訊安全管理系統 (ISMS) 顧問」→ 改成新領域
  • 規則 8「控制項消歧規則」中的 ISO 27001 控制項 → 改成新領域的高頻混淆概念
  • 規則 10 Markdown 格式中的「🛠️ 文件缺口」→ 可改成新領域慣用的名稱
💡 提示：如果你不確定新領域的「高頻混淆概念」是什麼，可以先不改規則 8， 跑完系統後觀察答案哪裡容易出錯，再回來補充。
5

更新術語加權與同義詞

讓搜尋引擎優先找到你的新領域核心術語。

打開 src/iso27001_advisor/core/search_tool.py，修改以下三個地方：

① 第 19 行：_SYNONYMS — 同義詞擴充字典

當使用者輸入 A，自動把 B 也加進搜尋。

# ISO 27001 原本的同義詞（刪掉這些）
"加密": ["密碼技術", "憑證"],
"弱點": ["技術脆弱性", "脆弱性"],

# GDPR 範例（依你的新標準自行填入）
"個資": ["個人資料", "PII", "data subject"],
"資料外洩": ["breach", "洩漏事件", "資料事故"],
"刪除權": ["被遺忘權", "right to erasure"],

② 第 47 行：_BOOST_WORDS — 核心主題詞加權

條文中包含這些詞時，搜尋排名自動提高。

# ISO 27001 原本的加權詞（清空後填入新領域的核心術語）
_BOOST_WORDS = [
    "資料主體", "同意", "資料控制者", "資料處理者",
    "資料保護官", "跨境傳輸", "隱私衝擊評估",
    "72 小時通報", "刪除", "更正",   # GDPR 範例
]

③ 第 53 行：_INTENT_BOOSTS — 問法意圖對應條文

當使用者的問法符合特定關鍵字組合，直接提升相關條文的排名。這是對抗「搜尋缺口」最有效的工具。

# 格式：{"ids": ["條文ID"], "keywords": ["關鍵字", ...]}
_INTENT_BOOSTS = [
    {
        "ids": ["article_17"],                    # GDPR 第 17 條刪除權
        "keywords": ["刪除", "被遺忘", "erasure"],
    },
    {
        "ids": ["article_33", "article_34"],       # GDPR 事件通報
        "keywords": ["資料外洩", "72 小時", "breach notification"],
    },
]
💡 提示：_INTENT_BOOSTS 的條文 ID 格式要和你在 Step 3 產出的 iso27001_structure.json 裡的 id 欄位一致。 先跑起來系統，觀察哪些問題找不到正確條文，再回來補這個清單。
6

重建向量索引

讓 Hybrid Search 能對新的條文做語意搜尋。

# 用新的知識庫重新計算每個條文的語意向量
python3 scripts/build_embeddings.py

這會在 data/ 產生：

  • data/embeddings.npy（所有條文的向量矩陣）
  • data/embedding_ids.json（ID 對照表）
⏳ 時間預估：首次執行需要下載約 120MB 的語言模型，之後每次重建約 1-2 分鐘。 看到「✅ 儲存：data/embeddings.npy」代表成功。

常見問題

Q：執行 app.py 出現 KeyError: 'type'

Step 3 的 JSON schema 修正沒有套用到。重新打開 scripts/build_new_advisor.py，確認每個 chunk 都有加上 type、section、subsection、title 四個欄位，然後重新執行 python3 scripts/build_new_advisor.py。

Q：搜尋結果完全不相關

Step 5 的 _SYNONYMS 和 _BOOST_WORDS 可能還沒更新，或者 PDF 切片太大（一個段落超過 1000 字）。嘗試在 build_new_advisor.py 把第 57 行的 1000 改小到 600，重新產生知識庫。

Q：系統說「在現有條文中找不到依據」

這代表 Step 3 的資料轉換可能有問題，或是術語不匹配。先用快速驗證指令確認知識庫有正確載入，再補充 Step 5 的 _INTENT_BOOSTS。

Q：想要同時保留 ISO 27001 和新領域兩套系統

Step 1 的「整包複製」就是為此設計的。兩個資料夾各自啟動在不同 Port 即可：

# 終端機 A（ISO 27001 版，預設 Port 5000）
cd iso27001-advisor && python3 app.py

# 終端機 B（新領域版，指定 Port 5001）
cd gdpr-advisor && python3 app.py --port 5001

Q：build_embeddings.py 找不到？

Phase 2 Hybrid Search 的腳本可能尚未建立。請參考 faithfulness_improvement_plan.html 的 Phase 2 Step 2-1，手動建立 scripts/build_embeddings.py。

Q：data/pdca_graph.json 是什麼格式？

這是合規推薦功能的來源。如果暫時不需要推薦功能，可以先用空檔案讓系統正常啟動（Step 3 末尾有指令）。等系統穩定後再研究格式，參考 docs/specs/system_spec.html 的架構說明。
